# Технические проверки (Technical Checks)

Инструкции по запуску технических проверок.

## 1. Область проверки

### Режим A (Task-based): Изменения по задаче
Запуск после `/resolve` или при наличии `TASK-[имя].md`. Принцип Fail-Fast:
1. **Список файлов** → `git status` / `git diff`. Без локальных изменений → сравнить ветку с `main` (`git diff main... --name-only`); на самой `main` → сравнить с предыдущим коммитом (`git diff HEAD~1... --name-only`). Пусто → переход к Режиму C.
2. **ESLint** → `npx eslint "путь_к_файлу"`. Ошибка → стоп → вызов `debug`.
3. **TypeScript** → `npx tsc -p tsconfig.app.json --noEmit`. Ошибка в измененных файлах → стоп → вызов `debug`.
4. **Тесты** → искать `*.test.ts/tsx` в той же папке / `__tests__`. Спросить разрешение юзера → запустить тест-ранер (`npm test -- "путь_к_тесту"` / `npx vitest run "путь"` / `npx jest "путь"`). Сбой → стоп → вызов `debug`.
5. **МСР-проверка требований (основной инструмент)**:
   - *Флаг `--fast`* → пропустить MCP (только статический анализ кода).
   - **Пинг браузера** → вызвать `get_plugins_status`. Ошибка → предупредить → спросить согласие продолжать без браузера.
   - **Инспекция кода** → каждая новая функция, новый метод или переменная должны быть проверены через MCP:
     - **Новые функции/методы** → сымитировать/вызвать выполнение (через UI/триггер в браузере) → прочитать стейт через `get_editor_state` или дерево через `get_items_tree` → убедиться в корректности рантайм-эффекта и отсутствии ошибок.
     - **Новые переменные/настройки** → проверить влияние на результирующий стейт/конфиг через `get_editor_state`, `get_editor_settings` или `inspect_item`.
     - **Инспекция элементов** → вызвать `inspect_item` или `get_item_by_id` для проверки измененных элементов дерева, корректности `parentId`, весов и геометрии.
   - Любое несоответствие требованиям или отсутствие MCP-валидации рантайма для новых сущностей → стоп → вызов `debug`.
6. **Сквозной вызов (Call-Chain)** → проверить путь события до стейта. Новая архитектура (Capabilities/Adapters в `model/types.ts`) имеет 1-й приоритет перед legacy.
7. **Архитектурный контроль (Опционально)** → `npm run lint:deps` (FSD) и `npm run lint:unused` (Knip/мертвый код) для проверки целостности структуры после завершения таска.

### Режим B (Targeted): Точечный аудит
При запуске вида `/check [путь]`:
1. **Линтер** → `npx eslint "путь"`. Ошибка → стоп → вызов `debug`.
2. **Типы** → `npx tsc -p tsconfig.app.json --noEmit` (фильтр по пути). Ошибка → стоп → вызов `debug`.
3. **Тесты** → спросить разрешение юзера → запустить тесты по пути (`npm test -- "путь"`). Сбой → стоп → вызов `debug`.
4. **Аудит** → проверка правил `.agents` (см. `./architectural_audit.md`). Нарушение → стоп → вызов `debug`.

### Режим C (Full): Полный аудит проекта
При флаге `--full` или отсутствии изменений/задач:
1. **Линтер** → `npm run lint` по всему проекту. Ошибка → стоп → вызов `debug`.
   - **FSD-архитектура** → `npm run lint:deps` (depcruise). Ошибка → стоп → вызов `debug`.
   - **Мертвый код** → `npm run lint:unused` (knip). Ошибка → стоп → вызов `debug`.
2. **Типы** → `npx tsc -p tsconfig.app.json --noEmit`. Ошибка → стоп → вызов `debug`.
3. **Тесты** → спросить разрешение юзера → запустить тесты проекта (`npm test`). Сбой → стоп → вызов `debug`.
4. **Аудит** → проверка всех новых и измененных файлов. Нарушение → стоп → вызов `debug`.
