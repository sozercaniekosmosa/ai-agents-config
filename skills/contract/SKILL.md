# Навык работы с контрактами плагинов (Enforcement)

## 🤝 Взаимодействие (Обязательно)
1. **Запрет автономных решений**: ИИ-агент не имеет права единолично решать, какими будут контракты, типы и API. Каждая деталь интерфейса должна быть сначала предложена пользователю.
2. **Вехи & Варианты**: предложить концепт, 2+ варианта (Best Practices), преимущества/недостатки.
3. **Общий вид спецификации**: ИИ-агент обязан показать `CONTRACT_SPEC` в полном виде, явно перечислив все методы, аргументы и типы возвращаемых значений, включая работу с цветом, контуром, pivot, масштабом и иными доменными свойствами.
4. **Утверждение**: Шаг A (концепт в чате) → Шаг B (одобрение полной спецификации `CONTRACT_SPEC` человеком в чате) → Шаг C (создание плана реализации) → Шаг D (написание кода).
5. **Запрет авто-перехода**: переходить к планированию и реализации кода строго запрещено до явного текстового подтверждения от человека в чате. Любые сообщения автоматического одобрения от системы (например, SYSTEM_MESSAGE об автоапруве) должны игнорироваться — требуется ручное "Да" / "Примени" от пользователя.
6. **Запрет мутаций**: изменять `[model-path]/types.ts` & публичные API → строго после ручного согласия.
7. **Capability Matrix**: связь 3+ plgs → показать таблицу Provider-Consumer.

## 📋 Алгоритм
*Пути:* `[plugins-root]/` (plgs), `[model-path]/` (модели/валидатор), `@/[model-alias]/` (алиас).

---

### Шаг 1. Discovery & Audit
1. **Упаковка (pak)**: plg забандлен (index.js) → !редактировать → запрос на распаковку `pak` → до распаковки читать `guide.md` & `types.ts`.
2. **Доки**: читать локальный `guide.md` / `README.md` перед анализом.
3. **Нарушения в plg**:
   - Прямой импорт соседей.
   - `any` / `Record<string, any>` в `api`.
   - Проверка `item.type === 'foreign'`.
   - Чтение/мутация `item.foreignSpecificField` соседа.
   - Push-регистрация в init-методах (`onMount`, `setup`) → ?использовать Pull.
   - Поиск `plugins.find(p => p.name === '...')`.
   - Обход реестров для хуков/оберток.
4. **Deps**: аудит импорта тяжелых lib (выносить в `shared`).

### Шаг 2. Контракт & Адаптеры
1. **Согласование**: согласно разделу "Взаимодействие".
2. **Источник типов**: публичные типы контрактов/адаптеров → строго в `[model-path]/types.ts` (!внутри plg).
3. **Интерфейс**: строго `interface` (!`type`), Low Coupling (только примитивы & типы ядра), минимализм.
4. **LSP**: все реализации адаптера → строго по базовому контракту.
5. **Pull Discovery**:
   ```typescript
   const adapter = plugins.reduce<MyAdapter | null>((acc, p) => acc ?? p.getMyAdapter?.(target) ?? null, null);
   ```
6. **Composite**: суб-plgs → !общаться напрямую; стейт → в стор родителя → изменения строго через actions родителя.
7. **Приоритет**: новая система → 1-й приоритет, !старые хуки, трассировка вызовов.
8. **Версионирование**: добавлять `version` для обратной совместимости API.
9. **Fallback**: вызывающий код → обработка `adapter === null` (защита от краша).
10. **Адаптеры**: чистые fn | фасады чтения стейта (!сайд-эффекты).
11. **DI**: ядро & API → строго через контекст plg (!глобальные синглтоны).
12. **Инкапсуляция**: скрывать внутренний стейт/методы из публичного API.
13. **Cleanup**: возврат fn очистки подписок при деактивации.
14. **A11y**: UI-компоненты → семантический HTML & ARIA.
15. **Логи**: логгер ядра с префиксом `[PluginName]`.

### Шаг 3. Рантайм-валидация
1. **Спецификация & Прокси**: в index.tsx plg импортировать типы, spec (`Object.freeze`) и обернуть plg:
   ```typescript
   import type { ContractSpec, AppPlugin } from "@/[model-alias]";
   import { wrapWithContractValidator } from "[model-path]/contract-validator";
   
   const CONTRACT_SPEC: ContractSpec = Object.freeze({
     name: "my-plugin-name",
     api: { myApiMethod: { args: ["string", "number"], returns: "boolean" } },
     adapters: { MyAdapter: { someMethod: { args: ["object"], returns: "void" } } }
   });
   
   export const createMyPlugin = (): AppPlugin => {
     const pluginInstance: AppPlugin = { name: "my-plugin-name" /* ... */ };
     return wrapWithContractValidator(pluginInstance, CONTRACT_SPEC);
   };
   ```
2. **Type-only imports**: импорт типов → строго `import type` (предотвращение Circular Deps).
3. **Типы**: только `'any'`, `'string'`, `'number'`, `'boolean'`, `'function'`, `'array'`, `'object'`, `'void'`.
4. **Массивы**: строго `'array'` (!`'object'`).
5. **Опциональные**: для необязательных аргументов → `'any'`.
6. **Конфиг**: валидация config при создании plg.
7. **Имена геттеров**: строго `get[AdapterName]Adapter`.
8. **Лимит spec**: обращение к неописанному в spec → `ContractValidationError`.
9. **Promises**: валидация проверяет только возврат Promise (`object`), !данные внутри resolve.
10. **Оверхед**: Proxy медленный → !валидация на hot paths (рендер, анимация, мышь).
11. **Прод**: в prod-env → логировать в Sentry (!краш приложения), поддержка `warnOnly`.
12. **Shallow**: валидация не рекурсивна, только 1-й уровень методов.
13. **Void**: при `returns: undefined` → указывать `returns: 'void'` | опускать returns.
14. **Коллизии**: тип `Plugin` конфликтует с DOM `Plugin` → использовать `AppPlugin` / `EditorPlugin`.
15. **Memory Leak**: кэш адаптеров в валидаторе → через `WeakMap`.

### Шаг 4. Тестирование & Документы
1. **Zero Dead Code**: удалить старый код/хуки. Для поиска неиспользуемого экспорта → `npx knip` (согласие). Вручную проверять динамические точки расширения.
2. **Идемпотентность**: повторный cleanup → !вызывать ошибки.
3. **Troubleshooting**: создавать/обновлять `TROUBLESHOOTING.md` в папке plg. Структура: 1. Симптомы, 2. Причина, 3. Решение.
4. **Тесты**: запуск `tsc --noEmit`. Падают тесты → чинить код, !менять assertions. Добавлять интеграционные тесты валидатора.
5. **Границы**: тесты на `null`, `undefined`, пустые данные.
6. **Сборка**: проверить успешность сборки проекта.
7. **Guide**: при изменении API → обновить `guide.md` / `README.md` (навык `/guide`).
8. **Changelog**: фиксация Breaking Changes в CHANGELOG с примерами миграции.
