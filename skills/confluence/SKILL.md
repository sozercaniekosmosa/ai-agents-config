# Навык Confluence

> [!CAUTION]
> **🚨 КРИТИЧЕСКОЕ ПРАВИЛО (СТРОГАЯ ОСТАНОВКА):**
> Категорически запрещено обновлять локальные данные (кеш/storage) или данные на сервере Confluence (вызовы `update_page`, `create_page`, `decompose_page` и любые операции синхронизации/слияния) без предварительного разрешения!
> **ВСЕГДА, СТРОЖАЙШЕ** останавливайтесь и запрашивайте явное согласие пользователя в чате перед выполнением этих действий.

Этот навык позволяет ИИ-агенту взаимодействовать с Atlassian Confluence, используя скрипт-посредник `middle.cjs`.

## Локальный VCS-кеш и Версионирование (Local Cache)

Скрипт `middle.cjs` интегрирован с модулем `storage.cjs` и пакетом `diff` для автоматического версионирования и кеширования локальных правок:
1. **Синхронизация по Timestamp**: Перед любым действием со страницей, `middle.cjs` проверяет `version.when` на сервере.
2. **Оптимизированное Хранилище (Index + Flat Storage)**: Для экономии токенов используется плоская структура по пространствам. Страницы хранятся в `.agents/skills/confluence/storage/{spaceKey}/` (файлы `{pageId}.current.xhtml` и `{pageId}.base.xhtml`).
3. **Единый Каталог**: Состояние всех страниц описано в одном легком файле `.agents/skills/confluence/storage/{spaceKey}/index.json`. Агенту достаточно прочитать его для поиска ID страницы.
4. **Генерация патчей (Дельты)**: При обновлении локальной копии (или разрешении конфликтов) генерируются `.patch` файлы в папке `commits/{pageId}_{commitId}.patch`.
5. **3-way Merge**: Если страница была изменена на сервере, а у агента есть локальные изменения, выполняется попытка слияния для предотвращения потери данных.
6. **Бесшовная интеграция**: Все action-вызовы (`get_page`, `update_page`, `create_page`, `decompose_page`) автоматически работают через локальный `storage.cjs`.

## Возможности

Скрипт `middle.cjs` поддерживает следующие действия (`action`):
- `get_page`: Получить удаленную страницу по ID (безопасное чтение без обновления кеша, возвращает статус локального кеша).
- `sync_page`: Синхронизировать локальный кеш с сервером (выполняет 3-way merge, может вернуть состояние конфликта).
- `get_local_page`: Прочитать текущую локальную версию страницы из кеша (включает локальные несохраненные правки).
- `get_page_by_title`: Получить страницу по коду пространства (`spaceKey`) и заголовку (`title`).
- `get_child_pages`: Получить список дочерних страниц по `pageId`.
- `get_attachments`: Получить список прикрепленных файлов по `pageId`.
- `create_page`: Создать страницу (поддерживает параметр `parentId` для создания дочерних страниц).
- `update_page`: Обновить существующую страницу (автоматически увеличивает версию, если `versionNumber` не указан).
- `delete_page`: Удалить страницу по ID.
- `search`: Поиск страниц через язык CQL (Confluence Query Language, поддерживает параметры `limit` и `start`).
- `get_spaces`: Получить список всех доступных пространств.
- `get_space`: Получить детали конкретного пространства по `spaceKey`.
- `get_comments`: Получить список комментариев к странице по `pageId`.
- `create_comment`: Создать комментарий к странице.
- `get_labels`: Получить список тегов (меток) страницы.
- `add_label`: Добавить новый тег к странице.
- `get_versions`: Получить историю версий страницы.
- `decompose_page` (или `create_subpages`): Пакетное создание дочерних подразделов для родительской страницы по `parentPageId` (с опциональным добавлением макроса `children` в родительскую страницу).
- `get_page_tree`: Получить иерархическое дерево дочерних страниц по `pageId` и `depth`.

## Использование (для Агента)

Вызывайте скрипт с пробросом файла `.env` через нативный флаг Node.js `--env-file=.agents/skills/confluence/.env`:

```powershell
node --env-file=.agents/skills/confluence/.env .agents/skills/confluence/scripts/middle.cjs '<JSON_PAYLOAD>'
```

Скрипт считывает параметры строго из `process.env`:
- `CONFLUENCE_URL`
- `CONFLUENCE_USERNAME` (если пустое → используется Bearer Auth / PAT; если заполнено → Basic Auth)
- `CONFLUENCE_API_TOKEN` (токен PAT или пароль)
- `CONFLUENCE_SPACE` или `CONFLUENCE_DEFAULT_SPACE` (опционально: подставляется по умолчанию, если `spaceKey` не передан в JSON)
- `CONFLUENCE_INSECURE_SSL` (опционально: `true` для работы с корпоративными SSL-сертификатами)
- `CONFLUENCE_TIMEOUT` (опционально: таймаут запроса в мс, по умолчанию 30000)

> [!NOTE]
> Если на сервере отключена Basic Auth (ошибка `Basic Authentication has been disabled`), необходимо оставить `CONFLUENCE_USERNAME=` пустым в `.env` и использовать Personal Access Token (PAT) в `CONFLUENCE_API_TOKEN`.

### Формат JSON-запросов

**1. Чтение страницы (get_page)**
```json
{
  "action": "get_page",
  "pageId": "12345"
}
```

**2. Чтение списка дочерних страниц (get_child_pages)**
```json
{
  "action": "get_child_pages",
  "pageId": "12345"
}
```

**3. Чтение прикрепленных файлов (get_attachments)**
```json
{
  "action": "get_attachments",
  "pageId": "12345"
}
```

**4. Чтение страницы по заголовку (get_page_by_title)**
```json
{
  "action": "get_page_by_title",
  "spaceKey": "DEV",
  "title": "Архитектура проекта"
}
```

**5. Создание страницы (create_page)**
```json
{
  "action": "create_page",
  "spaceKey": "DEV",
  "title": "Новая страница",
  "content": "<p>Содержимое страницы в формате XHTML/Storage</p>",
  "parentId": "67890"
}
```

**6. Обновление страницы (update_page)**
```json
{
  "action": "update_page",
  "pageId": "12345",
  "title": "Обновленный заголовок",
  "content": "<p>Новое содержимое</p>",
  "versionMessage": "Опциональный комментарий к версии"
}
```

**7. Удаление страницы (delete_page)**
```json
{
  "action": "delete_page",
  "pageId": "12345"
}
```

**8. Поиск с пагинацией (search)**
```json
{
  "action": "search",
  "cql": "space = DEV AND title ~ \"Архитектура\"",
  "limit": 10,
  "start": 0
}
```

**9. Декомпозиция / разбивка страницы на подразделы (decompose_page / create_subpages)**
```json
{
  "action": "decompose_page",
  "parentPageId": "12345",
  "includeChildrenMacro": true,
  "subpages": [
    {
      "title": "Подраздел 1: Настройки и конфигурация",
      "content": "<p>Содержимое подраздела 1...</p>",
      "labels": ["config"]
    },
    {
      "title": "Подраздел 2: API и контракты",
      "content": "<p>Содержимое подраздела 2...</p>",
      "labels": ["api"]
    }
  ]
}
```

**10. Получение иерархии / дерева страниц (get_page_tree)**
```json
{
  "action": "get_page_tree",
  "pageId": "12345",
  "depth": 2
}
```

### Запуск скрипта

Вызов с помощью `--env-file=.agents/skills/confluence/.env` (Powershell):
```powershell
node --env-file=.agents/skills/confluence/.env .agents/skills/confluence/scripts/middle.cjs '{\"action\":\"get_page\",\"pageId\":\"12345\"}'
```

Вызов через конвейер (`stdin`):
```powershell
$json = '{"action":"get_page","pageId":"12345"}'
Write-Output $json | node --env-file=.agents/skills/confluence/.env .agents/skills/confluence/scripts/middle.cjs
```

### Работа с временными файлами (ОБЯЗАТЕЛЬНЫЙ СТАНДАРТ)

1. **Запрет файлов вне `tmp/`**: Категорически запрещено создавать временные файлы (`scratch_*.html`, `payload_*.json` и т.д.) в корне проекта или других папках.
2. **Размещение в `tmp/`**: Все временные файлы (черновики, дамп-файлы HTML/XHTML, JSON-пейлоады) создаются СТРОГО в папке `.agents/skills/confluence/tmp/`.
3. **Авто-удаление пейлоадов**: При вызове `middle.cjs` с файлом передавайте флаг `--clean` для авто-удаления файла после обработки:
```powershell
node --env-file=.agents/skills/confluence/.env .agents/skills/confluence/scripts/middle.cjs .agents/skills/confluence/tmp/payload.json --clean
```
4. **Запрет редиректа stdout (>) в CLI Windows**: Категорически запрещено перенаправлять вывод команды `middle.cjs` в файл через оператор `>` в PowerShell (`> file.json`), так как это приводит к перекодированию в UTF-16LE / Mojibake. Передавайте параметр `--out .agents/skills/confluence/tmp/result.json` для безопасной записи результатов в UTF-8:
```powershell
node --env-file=.agents/skills/confluence/.env .agents/skills/confluence/scripts/middle.cjs .agents/skills/confluence/tmp/payload.json --out .agents/skills/confluence/tmp/result.json --clean
```
5. **Очистка директории**: Для полной очистки папки `tmp/` (всех файлов, кроме `.gitignore`) вызывайте:
```powershell
node --env-file=.agents/skills/confluence/.env .agents/skills/confluence/scripts/middle.cjs --clean-tmp
```

## Гуманизация и стиль текста (Humanization Guidelines)

При генерации контента для Confluence (создание/обновление страниц, комментарии, документация):

1. **Запрет ИИ-клише**:
   - Не использовать вступления и штампы ("В данной статье мы рассмотрим...", "Важно отметить, что...", "Подводя итоги...").
   - Избегать избыточной канцеляризмы и пустой "воды".

2. **Естественный инженерный стиль**:
   - Писать от лица опытного разработчика/техлида команды.
   - Сразу переходить к предметной сути (проблема → решения → конфигурация/код).
   - Использовать точные термины проекта и реальный контекст вместо обобщенных фраз.

3. **Живая структура**:
   - Избегать одинаковых механических списков ровно из 5 или 10 пунктов.
   - Использовать естественные абзацы разной длины и логичные заголовки.
   - Применять плашки `> [!NOTE]` и `> [!IMPORTANT]`, таблицы и блоки кода только там, где это облегчает чтение человеком.

4. **Строгий запрет эмодзи (Zero Emoji Policy)**:
   - КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО использовать любые эмодзи в заголовках, названиях страниц, подзаголовках, списках, таблицах, комментариях и тексте статей Confluence.
   - Для акцентов и смысловых блоков использовать только плашки `> [!NOTE]`, `> [!IMPORTANT]`, таблицы, жирный текст и `<code>`.

5. **Явное указание архитектурного слоя (Frontend/Backend) (ОБЯЗАТЕЛЬНЫЙ СТАНДАРТ)**:
   - КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО использовать абстрактные слова "код", "файлы", "модули" без контекста.
   - При ссылках на исходный код, пути к файлам или архитектуру **обязательно** явно указывать слой приложения: **Frontend** (клиентская часть, UI, React) или **Backend** (API, сервисы, БД).
   - Формулировки вроде "Реализация в кодовой базе" заменять на "Реализация во Frontend-модуле" или "Контракт на стороне Backend".

## Стандарты структуры страниц

Для страниц, описывающих объекты-потребители данных (компоненты, экранные формы, мнемосхемы, графики и т.д.), **СТРОГО** использовать стандартизированную структуру из 6 подразделов.
- Описание структуры хранится в файле: [data_consumer_page_template.md](references/data_consumer_page_template.md).
- Формат описания Data Flow («Запрос-Цепочка»): [data_flow_chain_format.md](references/data_flow_chain_format.md).
- Правила раздела 3 (**API-Контракты и Поток данных**):
  1. Раздел **API-Контракты описывается СТРОГО ДО Потока данных (Data Flow)** как в названии, так и в блоках текста.
  2. Для **каждого отдельного графика трендов и каждой отдельной таблицы** составляется собственный персональный блок API-Контракта и Data Flow.
  3. Эндпоинты оформляются **чистым текстом в тегах <code>** (без гипессылок).
При запросе на создание или обновление документации для таких объектов агент обязан руководствоваться этими шаблонами.

## Стандарты и регламент декомпозиции страниц

При декомпозиции / углублении структуры (разбиении крупной страницы на дочерние подразделы):

1. **Определение гранул декомпозиции**:
   - Страница разбивается на подразделы, если содержит автономные доменные блоки (например: отдельные виджеты, графики трендов, таблицы, подсистемы API).
   - Каждая выделенная сущность выносится в отдельную дочернюю страницу (`parentId` = ID родительской страницы).

2. **Автоматизация через `decompose_page`**:
   - Для выполнения разбивки использовать action `decompose_page` (или `create_subpages`), передавая `parentPageId`, список `subpages` (`title`, `content`, `labels`) и `includeChildrenMacro: true`.

3. **Оглавление и линковка на родительской странице**:
   - Родительская страница должна выступать обзорным хабом (Hub/Overview).
   - На родительской странице размещается макрос отображения дочерних страниц:
     `<ac:structured-macro ac:name="children"><ac:parameter ac:name="all">true</ac:parameter></ac:structured-macro>`
   - При необходимости добавляется макрос `toc` (Table of Contents):
     `<ac:structured-macro ac:name="toc" />`

4. **Единый визуальный и структурный стиль подразделов**:
   - Дочерние подразделы наследуют теги пространства и метаданные.
   - Каждый подраздел оформляется по стандарту [data_consumer_page_template.md](references/data_consumer_page_template.md) при совпадении назначения.

5. **Именование и позиционирование метки/модуля в заголовках**:
   - Название/префикс модуля (например, `[CemisPumpsUnit]` или `[CemisPumps]`) указывает имя системы/компонента.
   - В заголовке **родительской страницы** префикс модуля указывается в начале строки: `[CemisPumps] — Сводный дашборд...`
   - В заголовках **всех дочерних страниц** название модуля помещается строго **в конец строки**: например, `1. Обзор и Назначение (Overview & Context) [CemisPumps]`.
   - **Строгий запрет и аудит**: Никакой дочерний подраздел НЕ ДОЛЖЕН начинать своё имя с префикса модуля `[ModuleName]`. При обнаружении существующих дочерних страниц с префиксом в начале названия, агент обязан провести их аудит и переименовать, переместив префикс модуля в самый конец строки.

6. **Очистка родительской страницы после декомпозиции (Zero Duplication)**:
   - После успешного переноса контента в дочерние подразделы, продублированный контент **ОБЯЗАТЕЛЬНО удаляется** из родительской страницы.
   - В родительской странице (Overview Hub) оставляются только: вводное описание, общие/сводные данные (например, глобальный маппинг параметров) и макрос `children` со ссылками на созданные подразделы.
   - **Строгое правило нумерации и дублирования:** Если раздел сохраняется на родительской странице, для него **НЕ создается** отдельный дочерний подраздел. При этом из заголовка такого раздела **удаляется порядковая нумерация** (например, вместо `3.6. Маппинг...` пишется `Маппинг...`), чтобы этот раздел логически не выбивался из нумерации вынесенных дочерних подразделов.
