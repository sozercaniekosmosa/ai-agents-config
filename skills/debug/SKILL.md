Этот навык предназначен для локализации и устранения багов в приложении путем рантайм-исследования через MCP, автоматической/ручной инъекции `[DEBUG]`-логов, визуального сохранения холста при падении и двойной очистки кода.

---

## Принципы и ограничения

1. **Zero-Code-Change First (Приоритет MCP-исследования)**:
   - Прежде чем писать какой-либо логгер на диск, агент обязан использовать встроенные методы рантайм-инспекции (MCP). Изменение файлов на диске — это вторичная мера для сложных случаев.

2. **Запрет симптоматического рефакторинга**:
   - ЗАПРЕЩЕНО переписывать, удалять или рефакторить компоненты/плагины только потому, что баг визуально проявляется во время их работы.
   - Любое изменение кода должно быть предварено точным пониманием того, какая именно переменная или функция ломает контракт.

3. **100% Автономность и отсутствие внешних зависимостей**:
   - Все вспомогательные скрипты хранятся внутри `.agents/skills/debug/scripts/`.
   - Запрещено менять `package.json`, `vite.config.ts` или устанавливать внешние npm-пакеты ради отладки.

4. **Игнорирование скомпилированных JS-бандлов**:
   - Строго запрещено открывать, читать или изменять файлы `index.js` в директориях плагинов (они являются обфусцированными бандлами).
   - Если дебаг упирается в код забандленного плагина, необходимо немедленно приостановить работу и запросить распаковку через `/pak` в чате у пользователя.

5. **Использование Базы Знаний**:
   - Перед развертыванием тяжелого логирования прочитайте базу данных типичных багов проекта в `TROUBLESHOOTING.md`. Большинство проблем уже имеют готовые рецепты решений.

6. **Двойной контур очистки**:
   - Любое изменение кода должно быть обернуто в маркерные комментарии `// === START DEBUG AGENT ===` и `// === END DEBUG AGENT ===`.
   - После завершения отладки запуск скрипта `cleanup.cjs` обязателен. Если скрипт падает с ошибкой, агент обязан исправить все остаточные маркеры вручную.

7. **Локальный Troubleshooting (TROUBLESHOOTING.md)**:
   - При исправлении ошибок в конкретном плагине/модуле, агент обязан создать или обновить локальный файл `TROUBLESHOOTING.md` непосредственно в папке этого плагина.
   - В локальном файле фиксируются симптомы, причина и решение в обобщенных архитектурных терминах для переносимости.

## Этапы работы навыка

### Этап 0: Zero-Code-Change & База Знаний (ОБЯЗАТЕЛЬНЫЙ СТАРТ)

> [!IMPORTANT]
> **Принцип минимизации затрат:** Если баг простой (NaN в расчетах, неверное значение свойств, ошибки типов, опечатки), агент обязан ограничиться рантайм-исследованием через МСР-инструменты и поиском в Базе Знаний. Внедрение логов на диск и запуск сервера (Этап 1) разрешены только для сложных багов (асинхронные гонки, утечки памяти, рендер-штормы), если Этап 0 не дал результатов.


1. **Поиск готового решения**:
   - Прочитайте глобальный файл `.agents/skills/debug/TROUBLESHOOTING.md` и локальный файл `TROUBLESHOOTING.md` в папке целевого плагина (при его наличии) на предмет схожих симптомов (NaN в расчетах, утечки событий, асинхронные ошибки).

2. **Инспекция состояния приложения и элементов**:
   - Вызовите доменные MCP-инструменты (например, `get_editor_state` / `get_app_state`) для получения состояния сторов, активных элементов и истории.
   - Используйте `get_items_tree` или аналог для получения структуры дерева компонентов/элементов.
   - Используйте `get_plugins_status` для проверки статуса активных модулей/плагинов и доступных адаптеров.
   - Используйте `inspect_item(id)` или аналог для глубокой инспекции конкретного узла или сущности в рантайме.

3. **Рантайм-эксперименты с мутацией и перезагрузкой**:
   - Проверьте гипотезу, изменив свойства элемента через доменные MCP-инструменты мутации (`mutate_items` или аналог).
   - Если баг вызвал некорректное состояние UI, используйте `reload_browser` для сброса рантайм-сессии без сброса кода.
   - **Если браузер закрыт/завис или таймаут MCP** → запустить его в интерактивной сессии пользователя: получить имя пользователя через `whoami`, затем `schtasks /create /tn "OpenBrowserForAgent" /tr "cmd.exe /c start http://localhost:3001" /sc once /st 00:00 /ru <ИМЯ_ПОЛЬЗОВАТЕЛЯ> /it /f`, затем `schtasks /run /tn "OpenBrowserForAgent"` и `schtasks /delete /tn "OpenBrowserForAgent" /f`.

4. **Приостановка при обнаружении бандлинга**:
   - Если стек вызовов ошибки указывает на скомпилированный плагин (файл `index.js` в директории плагина), агент **обязан** остановить отладку и написать в чат:
     * *«Для продолжения анализа необходимо распаковать забандленный плагин. Пожалуйста, подтвердите запуск команды `/pak` с распаковкой для плагина [название]»*.
     * **СТРОГО ЗАПРЕЩЕНО** запускать `unpack` без согласия пользователя.

### Этап 1: Инъекция логов и запуск сервера

Если баг лежит в асинхронных расчетах, цепочках событий или ре-рендерах, переходим к инъекции.

1. **Запуск сервера логов**:
   - Проверьте доступность MCP-сервера логов. Если недоступен, запустите резервный:
     ```bash
     node .agents/skills/debug/scripts/logger-server.cjs
     ```
     *(Использовать `run_command` в фоновом режиме)*. Порт сервера по умолчанию `9998` (или из `.logs/port.json`).

2. **Выбор способа инъекции**:

   * **А) Автоматическая инъекция через CLI-помощник (РЕКОМЕНДУЕТСЯ)**:
     Для встраивания логов используйте встроенный инжектор:
     ```bash
     node .agents/skills/debug/scripts/inject.cjs <filepath> <functionName> <logType>
     ```
     Где `logType` может быть:
     - `log` — инжектирует в начало функции логирование входных параметров (arguments в JSON) и в конец выходной маркер.
     - `performance` — вставляет замеры времени выполнения `performance.now()`.
     - `timeline` — логирует только время триггера события.
     - `render-tracker` — отслеживает количество рендеров функционального React-компонента.
     - `event-listener` — логирует регистрацию слушателя события и стек-трейс вызова.

   * **Б) Ручная инъекция расширенного хука**:
     Внедряется строго между `// === START DEBUG AGENT ===` и `// === END DEBUG AGENT ===` в начало главного файла (например, `App.tsx` / `MainComponent.tsx`).
     Этот хук перехватывает ошибки, Promise Rejections и отправляет снимок состояния приложения при критическом сбое.
          Прочитайте содержимое файла-шаблона `.agents/skills/debug/resources/global-hook.ts` с помощью `view_file` и вставьте его в код.

3. **Специализированные ручные логгеры**:
   При необходимости детальной отладки конкретных подсистем используйте готовые шаблоны из папки `resources/`:
   
   * **Мониторинг Zustand-стора (State Change Diff)**:
     Используется для отслеживания изменений в состоянии. Прочитайте содержимое `.agents/skills/debug/resources/zustand-logger.ts` и внедрите его в код.
     
   * **Детектор утечек подписок (Event Listener Interceptor)**:
     Используется для выявления неочищенных слушателей событий мыши/клавиатуры. Прочитайте содержимое `.agents/skills/debug/resources/event-leak-monitor.ts` и внедрите его в код.

### Этап 2: Вычит результатов, Snapshot-инспекция и Cross-Module Audit

1. **Вычит результатов**:
   - Вместо сканирования огромного файла `runtime.log` сначала проверьте структурированные отчеты:
     * `.agents/skills/debug/.logs/debug-report.json` — JSON с частотой ошибок, рендеров и утечек.
     * `.agents/skills/debug/.logs/debug-summary.md` — красивый markdown-отчет о прошедшей сессии.
   - Прочитайте детальные логи из `.agents/skills/debug/.logs/runtime.log` для точной последовательности событий. При выводе выдержек из логов в чат сжимать их по правилам `.agents/skills/short/SKILL.md`.
   - Если произошел графический или рантайм-сбой, проверьте файл снимка состояния в `.agents/skills/debug/.logs/` для визуального анализа в момент падения.
   - Изменения Zustand стора будут представлены в виде красивого diff-дерева в логе благодаря обработчику `logger-server.cjs`.

2. **Кросс-модульный аудит**:
   - При обнаружении багов в одном из модулей/плагинов, проверьте все аналогичные смежные модули на наличие такого же паттерна.

---

### Этап 3: Очистка кода и Git Pre-Commit Guard

1. **Автоматическая очистка**:
   - Запустите скрипт зачистки кода:
     ```bash
     node .agents/skills/debug/scripts/cleanup.cjs
     ```
   - Если запуск завершился с кодом ошибки `exit code 1` (Double-Pass Verification обнаружил незакрытые маркеры или остаточные слова), исправьте все остаточные участки кода, перечисленные в ошибке, вручную.

2. **Настройка Git Pre-Commit Guard (Рекомендуется)**:
   - Для предотвращения коммита дебаг-кода разработчиком, добавьте запуск очистки в git hooks. Например, в `package.json` или Husky:
     ```json
     "pre-commit": "node .agents/skills/debug/scripts/cleanup.cjs"
     ```
     *(Или запускайте команду перед каждым git commit)*.

3. **Применение исправления**:
   - Примените точечное исправление непосредственно в код проекта.

4. **Документирование ошибки (TROUBLESHOOTING.md)**:
   - При исправлении ошибок в кодовой базе плагинов/модулей, создайте или обновите локальный файл `TROUBLESHOOTING.md` в папке соответствующего плагина. Задокументируйте симптомы, причину и решение в обобщенных архитектурных терминах.
